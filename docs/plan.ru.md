## План усиления людей, трекинга и СИЗ после изучения Framework

Это план новых экспериментов, а не описание уже обученной модели. Текущий сайт и runtime при разборе SDK не менялись. Совместимость SDK и качество на промышленном видео пока не измерены.

### Найденные ограничения текущего кода

- Основная модель - `yolov8n-pose.pt`, инференс на 640. Человек ищется через nano pose-модель; независимого сильного детектора людей нет.
- `PeopleTracker.update()` отбрасывает наблюдения с confidence ниже `RunConfig.confidence=0.4` даже после сопоставления ByteTrack. Низкоуверенное наблюдение может поддерживать ID внутри tracker, но исчезает из результата и визуализации. Это доказанный механизм пропусков, но причина конкретного видео с зеркалом требует воспроизведения.
- PPE - готовая сторонняя YOLOv8s ONNX на 640, `CPUExecutionProvider`, порог `object_confidence=0.5`. Повторный crop-проход есть только для телефона, для головы/торса его нет. Собственной валидации СИЗ нет.
- Привязка каски к человеку использует геометрическую верхнюю часть bbox (40% высоты), а не полноценную локализацию головы. При близких людях неоднозначное соответствие превращается в unknown.
- Статус СИЗ пересчитывается для каждого кадра. При конфликте каска/нет каски сейчас всегда побеждает положительный класс; при отсутствии прямого отрицательного класса - unknown. Это может давать пропуски и мигание статусов.

### Выбранная архитектура

1. **Основной кандидат для LinQ - YOLO12m**, отдельно дообученный на людях/головах и отдельно на СИЗ. Он явно указан в SDK, есть рецепт с частичным FP16 и PIECEWISE_LUT. Начать с воспроизведения совместимого экспорта и маленькой калибровки до дорогого обучения. Не считать YOLO12x автоматически поддержанным из-за поддержки YOLO12m.
2. **Второй кандидат - YOLOv8m-seg** из списка SDK. Сравнить recall людей и пользу масок на перекрытиях. Использовать только если дополнительное качество оправдывает ресурсы; не требовать segmentation-разметки у всех PPE-данных.
3. Pose отделить от наличия человека. Совместимый `yolov8n_pose` оставить для признаков позы; отсутствие надёжных keypoints не должно убирать bbox человека. Более сильную pose-модель можно сравнить на NVIDIA, но LinQ-совместимость ей не приписывать.
4. **Классификаторы головы и торса**: дообученные ResNet50, затем сравнение с ResNet152/EfficientNet-B4, присутствующими в SDK. Две независимые задачи: `helmet / bare_head / unobservable` и `vest / no_vest / unobservable`; добавить спорную/невалидную область в unknown. Веса ImageNet сами каски не распознают. Новую голову и preprocessing отдельно проверять компилятором.
5. Обучение и NVIDIA-референс - Kaggle в изолированном окружении. Тяжёлые YOLO12x / YOLO26x допустимы как исследовательские teachers для проверки разметки и distillation в YOLO12m. GPU и доступную память проверить в конкретной Kaggle-сессии; два устройства не образуют один общий буфер VRAM. SDK Linux/Python 3.12 держать отдельно от окружения обучения и Windows-сервера.

Предлагаемый конвейер: кадр -> детектор людей/голов -> tracker -> области головы и торса -> PPE-детектор + специализированные классификаторы -> привязка к ID -> проверка видимости и накопление подтверждений -> событие/клип/журнал.

На первом этапе оставить один основной детектор. Добавлять модели по одной с измерением вклада; если вторая не улучшает validation на сложных сценах, не включать её в рабочую цепочку.

### Люди, зеркала и устойчивость ID

- Сначала сохранить короткие проблемные последовательности с разметкой bbox/ID: человек перед зеркалом, отражение, вход/выход из кадра, перекрытие, поворот спиной, лежащий человек, темнота. Отделить настоящий пропуск детектора от провала confidence, ID switch и ошибки подавления дубликатов.
- Разделить пороги `new_track`, `association`, `display` и `alert`. Продолжать существующий трек по более слабому реальному наблюдению, но не создавать по такому кадру новую подтверждённую тревогу.
- Сравнить настроенный ByteTrack с BoT-SORT и appearance-сопоставлением. Подтверждённый ID можно кратко сохранять при пропуске; прогнозная рамка должна явно помечаться и не считаться новым наблюдением нарушения. Начальные окна 0.5-1.5 с - гиперпараметры, выбираемые по validation, не гарантия качества.
- В зеркале отражение часто визуально совпадает с человеком; ReID само по себе не решает этот случай. Для фиксированных камер добавить отдельную маску отражающей поверхности и учитывать реальную область пола/сегментацию. Нельзя отбрасывать всякий bbox, пересекающий зеркало: настоящий человек может стоять перед ним. Отдельно проверить отсутствие двойных тревог по отражению.
- Сравнить размеры входа 640/960/1280 на NVIDIA. Для LinQ каждый размер отдельно проверять и компилировать; альтернативно анализировать плитки исходного кадра совместимым статическим входом 640, корректно объединяя координаты. Плитки и crop не восстанавливают отсутствующие пиксели маленькой головы.

### СИЗ и ансамбль

- Искать каску/непокрытую голову на вырезке головы, жилет/его отсутствие на торсе. Геометрию уточнять локализацией головы/keypoints, когда они надёжны. Сохранять координаты в исходном кадре и связь с ID; при неоднозначной привязке не переносить экипировку соседу.
- Согласовывать независимые источники: PPE-детектор и классификатор crop. Калибровать scores на validation. При сильном конфликте показывать unknown и причину; правило «найдена любая каска - значит каска надета» заменить сопоставлением доказательств одного человека.
- Не выводить «без каски» просто из отсутствия бокса каски. Нужна видимая непокрытая голова или уверенный отрицательный класс crop-классификатора. Для жилета - достаточно видимый торс с подтверждённым `no_vest`. Неполная разметка другого датасета не является отрицательным примером.
- Сглаживать результаты по времени и качеству видимых кадров: например, 3 уверенных наблюдения из последних 5 плюс минимальная длительность. Не подтверждать нарушение по прогнозным bbox и повтору устаревшей классификации. TTL должен переводить старый статус в unknown, а ID switch сбрасывать накопленные признаки.
- Для офлайн-анализа можно сравнить ансамбль YOLO12m + YOLOv8m-seg для людей, с объединением одинаковых классов и подавлением дубликатов. Не сливать классы `helmet` и `no_helmet` через WBF и не усреднять некалиброванные scores моделей.
- Для live использовать каскад: второй анализ только для неуверенных/конфликтных результатов и периодической проверки, с ограниченным числом crop и длиной очереди. Если суммарное время хуже частоты поступления кадров, показывать задержку и пропуск кадров, не накапливать бесконечную очередь.
- В UI разделить «не видно голову», «слишком мелко», «неоднозначная привязка», «модели расходятся», «наблюдение устарело», «СИЗ не проверяется». Сохранять модель, версию, фактическое время наблюдения и crop-доказательство в карточке события. Это объясняет unknown оператору.

### Данные и условие увеличения в четыре раза

В проекте используются готовые PPE-веса, а не уже подготовленный собственный большой train-набор. Поэтому нельзя утверждать, что добавление нескольких тысяч фотографий автоматически увеличит обучение модели в четыре раза.

По текущей [карточке SafetyVision](https://huggingface.co/ayushgupta7777/safetyvision-yolov8) upstream v2 использует 80 304 изображения суммарно и 68 253 train. Для честного сравнения с этой заявленной базой четыре train-объёма - **273 012** пригодных уникальных train-изображений. Это ориентир по карточке автора, не проверенный нами состав исходного обучения. Для собственного корпуса сначала зафиксировать `N0` после очистки, затем требовать `Nnew >= 4*N0` с одинаковой единицей подсчёта. Дополнительно считать число независимых видео/камер и экземпляры каждого класса; несколько почти одинаковых соседних кадров не считать новым разнообразием. Умножение аугментациями не равно четырёхкратному росту исходных данных.

| Источник | Что даёт | Ограничение при объединении |
|---|---|---|
| [SHWD](https://github.com/njvisionpower/Safety-Helmet-Wearing-Dataset) | 7 581 изображение, каски и головы без касок | Разметку головы нельзя напрямую приравнять bbox целого человека; проверить баланс и происхождение/условия данных |
| [SH17](https://github.com/ahmadmughees/SH17dataset) | 8 099 изображений, 17 классов, промышленная среда и части тела | CC BY-NC-SA 4.0; нет готовых отрицательных классов `no_helmet/no_vest`; собственная разметка видимости нужна |
| [Construction-PPE](https://docs.ultralytics.com/datasets/detect/construction-ppe) | 1 416 изображений, парные классы ряда СИЗ | Нет отдельного `no_vest`; AGPL-3.0, часть примеров уже использовалась для демонстрации, их исключить из независимого теста |
| Датасеты из upstream PPE-корпуса | Продолжение базового обучения с известной схемой | Нужны фиксированные версии, проверка доступности, условий каждого источника, неполных меток и пересечений |
| Новые реальные видео и вручную проверенные кадры | Зеркала, головы без касок, торсы без жилета, реальные ракурсы камер | Основной источник доменного разнообразия; на train и test разные исходные сцены и сессии |

Перечисленные три открытых набора вместе дают 17 096 изображений **до** пересечений и очистки; одних их недостаточно для четырёхкратного расширения заявленной upstream базы. Основной новый объём придётся получать из дополнительных разрешённых видеоданных и разметки; подтверждённого корпуса на 273 тыс. train-изображений пока нет.

Подготовка: единая онтология `person/head/helmet/bare_head/vest/no_vest`, область и видимость каждого атрибута, исходный dataset/class, источник и лицензия. Head-level боксы и person-level отрицательные метки не смешивать в одну геометрию. Для неполной разметки - доразметка или обучение отдельных задач, не молчаливое превращение отсутствующих классов в фон. SHA-256 плюс perceptual dedup, кластеризация соседних кадров, группировка исходных видео/камер/сессий до split. Готовые test-splits источников не переносить в train. Teacher-псевдометки использовать только для train после ручной проверки сложных и отрицательных случаев; test размечать независимо.

### Этапы обучения и проверки

1. Зафиксировать текущую модель/хеши/config, собрать отдельный набор ошибок и baseline-отчёт. Сцену с зеркалом, использованную для отладки, оставить regression/validation; финальный test - другие сцены.
2. В Linux 3.12 воспроизвести экспорт/разрез/калибровку/компиляцию YOLO12m на маленьком train-подмножестве. При проблемах использовать совместимый запасной граф, не ждать конца большого обучения.
3. Собрать и проверить manifest корпуса. Сначала пилот на меньшем чистом наборе: проверить согласованность классов, learning curves, recall отрицательных СИЗ и видимость. Затем основной объём; 100-200 эпох - стартовый диапазон экспериментов, фактическое число определяется validation и ресурсами.
4. Kaggle: отдельные запуски детектора людей, PPE-детектора, двух crop-классификаторов. Mixed precision, подбор batch под реальную VRAM, checkpoint/resume, фиксированные seeds/commit/данные. Для крупных teachers и high-resolution batch может быть маленьким; throughput измерить на пилоте. Полный четырёхкратный корпус и ансамбль - более длительная работа, их готовность к дедлайну без замеров не обещать.
5. Сравнить последовательно: baseline -> усиленный детектор -> tracker/пороги -> head/torso crops -> временное сглаживание -> ансамбль. Каждому изменению отдельная ablation, все пороги и веса по validation. Сохранить регрессии падений, зон, огня и поведения.
6. После выбора FP32 модели: 300-1000 разнообразных train-кадров/crop как начальный калибровочный бюджет, с измерением результата и расширением при необходимости. Не использовать test. Воспроизвести mixed-precision рецепт, проверить до/после threshold fine-tuning. Это проектный бюджет, не требование SDK и не гарантия достаточности.
7. Экспортировать полный ONNX и разрезанные head/tail, thresholds, tensor manifest, class map, preprocessing, хеши и `.tpu`. Выполнить паритет на последовательностях и замер LinQ. Без устройства статус только `compiled_unverified`, без успешной компиляции - `not_compiled`.
8. После интеграции прогнать сайт кликами: live и загрузка видео, различимые measured/predicted bbox, понятный unknown, отсутствие повторов зеркального события, правильные алерты, тайминги и клипы. Реальную камеру подключать в согласованном тестовом сценарии.

### Критерии приёмки

- Отдельные Precision/Recall/F1 для `no_helmet` и `no_vest`, event-level one-to-one matching с допуском времени, без объединения трудных классов в одну высокую общую accuracy. Цель **каждое P/R/F1 > 0.95** на закрытом независимом наборе; это целевые критерии, а не обещанный результат.
- Bounding-box mAP50 и mAP50-95 отдельно от event F1. Для людей: recall по размеру/освещению/перекрытию, число ID switches и длительности разрывов на видимых людях.
- Для unknown: доля на реально видимых и пригодных для проверки головах/торсах, selective coverage и качество на полном наборе пригодных случаев. Если нарушение пригодно для оценки, но система ответила unknown, учитывать как пропуск, а не выбрасывать из recall. Полностью невидимые атрибуты оценивать отдельно.
- Ложные тревоги на час, дубли на эпизод, задержка подтверждения, успешность сохранения клипа; отдельные результаты на зеркалах и плотной группе людей. Предварительный бюджет live P95 от начала нарушения до тревоги 2.5 с при `ppe_hold=1.5` с и не более 1 с на обработку/очередь; подтвердить замером или пересмотреть требования явно.
- Паритет после квантования: желаемая потеря event F1 не более 0.01 абсолютного значения и сохранение целевых P/R/F1. При провале менять калибровку/точность операций, а не объявлять целевой результат достигнутым.
- Публиковать число независимых видео, положительных/отрицательных эпизодов и интервалы неопределённости; малый удачный набор не подтверждает промышленное качество. Финальный test не использовать для дальнейшего подбора.

## Реализация на 24.10.2026

Linux smoke-компиляция **YOLO12m** завершена успешно: SDK 2026.9.45, Python 3.12.11, TPU_H1M/O1, FP16 Reduce и PIECEWISE_LUT. Файл `.tpu` получен, отчёт `docs/yolo12m-compatibility.json`; запуска платы и измерения качества после квантования нет.

В рабочий конвейер добавлены независимый YOLO12m для людей, привязка позы, сохранение слабых наблюдений ByteTrack, краткая помеченная рамка при пропуске, зона исключения отражений, PPE crop-проходы и явные причины unknown. Слабые/сохранённые наблюдения не подтверждают новые тревоги. Неправильное принятие обычной одежды за жилет всё ещё встречается у исходных весов; это зафиксировано в smoke-отчёте.

Корпус расширен четырьмя скачанными источниками; фактические размеры после дедупликации публикуются в `docs/ppe-dataset-summary.json`. Crop считаются отдельно от исходных изображений. Готов самодостаточный `notebooks/LinQ-PPE-Kaggle.ipynb`: smoke/full, resume, три детектора, два ResNet152, validation-пороги, итоговый test, экспорт. Классификаторы используют PPE proposal с контекстом 1.3 как при обучении; произвольный person crop не подменяет эту геометрию. Они не запускаются без подготовленных весов.

Следующие внешние этапы: обучение в Kaggle, ручная проверка crop/видимости, независимые целевые видео, повторная компиляция дообученных графов и реальный LinQ-бенчмарк. Ансамбль расширять после измеренного выигрыша. Метрики >0.95 и четырёхкратное расширение upstream корпуса не объявлены достигнутыми.

## Что требуется по кейсу

На слайдах 4, 7 и 13 описан сервис видеоаналитики промышленной безопасности. Приоритет — насколько быстро и достоверно система сообщает о нарушении, а не максимальное число распознаваемых классов.

Обязательны:

1. Видеопоток или тематические изображения как вход.
2. Распознавание с помощью нейросетевой модели.
3. Оперативное сообщение в Web/GUI: доказательство, камера, время, тип.
4. Подавление повторов: один длительный эпизод — одно сообщение.
5. Журнал с фильтрами по типу, камере, зоне и времени.
6. **Инференс на LinQ с измерениями скорости.** Локальный NVIDIA-бенчмарк этого не заменяет.

Желательны визуальная настройка зон, статистика, подтверждение/отклонение оператором и несколько потоков. На слайде 13 прямо разрешён выбор приоритетных сценариев при расширяемой архитектуре.

Сценарии: бег/резкие перемещения, опасное сближение с техникой, телефон, курение/огонь, преодоление ограждений/проход под грузом, высота без страховки, падение/лежание, неправильная переноска груза как дополнительный случай. Поэтому проект, который показывает только каски и жилеты, охватывает задачу недостаточно.

## Рекомендуемый MVP

Сначала фиксированная камера, один видеофайл и 2 базовых правила:

- Настраиваемая запретная зона. Детектор людей → ByteTrack → нижний центр bbox в полигоне → выдержка → одно событие.
- Быстрое перемещение по траектории. Это доступный признак потенциально опасного движения; термин «бег» требует отдельной валидации на ходьбе/беге.

Обновление: падение дополнено обученным RGB ResNet18. Независимые 20 последовательностей дали event P/R/F1=0,90; целевые >0,95 не достигнуты. Кадровый F1=0,613. Полный протокол — в validation.md и quality_report.json.

Обновление: дополнительные модели и правила сценариев подключены; матрица условий и ограничений находится в scenarios.ru.md. Сближение оценивается для распознанного движущегося транспорта или по размеченной оператором опасной области. В стандартном COCO нет отдельного класса «погрузчик», поэтому нельзя просто переименовать truck в forklift.

## Нейросети и архитектура

В прототипе выбран YOLOv8n-pose: одна маленькая свёрточная модель даёт людей и ключевые точки тела. Готовая COCO-модель позволяет запустить продукт без обучения. ByteTrack, временные правила, БД и интерфейс выполняются на CPU и не привязаны к CUDA.

Это кандидат для переноса, а не подтверждённая поддерживаемая LinQ модель. Выбор финальной нейросети зависит от SDK. Если pose-граф не компилируется, сначала перенести совместимый детектор людей и завершить зоны/движение; поддержку позы решать отдельно.

Схема:

```text
видео → кадры → [нейросеть PyTorch / LinQ] → bbox + keypoints
                                               ↓
                                    ByteTrack → правила во времени
                                               ↓
                                событие → SQLite + кадр + видеоклип
                                               ↓
                                 Web-журнал → проверка оператором
```

Для TPU оставлять на хосте decode/NMS, если эти операции не поддерживаются компилятором. Экспортировать статическую форму batch=1. Размер и opset брать из документации SDK; имеющийся ONNX с opset 12 — только проверяемый референс. Квантование делать средствами LinQ SDK с его требованиями, а не слепо экспортом TensorRT/Coral.

В кейсе не назван конкретный «существующий продукт». Утверждать, что один из найденных продуктов и есть подразумеваемое авторами решение, оснований нет. Также не установлено, на каких именно GPU работают все перечисленные коммерческие продукты.

Проверенный дефект Construction AI: `FallDetector.update()` возвращает `raw_state` при неподтверждённом состоянии; если `raw_state == possible_fall`, такая метка может выйти до подтверждения. В нашем коде событие создаётся отдельным временным Gate после выдержки; для него написаны тесты на одиночный ошибочный кадр и пропуск наблюдения.

Основное переиспользование в проекте — проверенные библиотеки и обученные веса. Самостоятельная инженерная часть для защиты: отделение исполнения модели, правила времени, фильтрация повторов, журнал, воспроизводимая оценка и перенос на отечественный ускоритель.

## Что измерять

- Event Precision / Recall / F1 с однозначным сопоставлением один к одному.
- Ложные тревоги на час нормальной записи.
- Число повторных тревог на один эпизод.
- Время видео от начала размеченного события до тревоги.
- Медиана/P95 инференса, decode/pre/post-process отдельно, полный конвейер, экспорт.
- На LinQ: те же кадры/размер/batch, версия SDK, модель и её хеш, число потоков, длительность теста, качество до/после квантования.

Условия измерения локальных прогонов записываются в `metrics.json`. Короткий локальный файл не подтверждает возможность обслуживания множества live-камер.
