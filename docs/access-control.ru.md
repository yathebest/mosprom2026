# Предприятия и права доступа

Роли кейса взяты со страниц 9–11 `docs/reference/КЕЙС_LinQ.pdf`. Администраторы платформы и предприятия добавлены по продуктовой постановке пользователя. Из Ortouz использованы архитектурные принципы: глобальные и локальные разрешения, проверка permissions на сервере и фильтрация данных по текущему предприятию. Код Ortouz и его медицинские роли не копируются.

| Роль | Возможности |
| --- | --- |
| Администратор платформы | Создание предприятий и приглашение локальных администраторов по одноразовой ссылке; рассмотрение заявок, отклонение с причиной, приостановка и восстановление предприятий, глобальный журнал. Данные камер доступны после явного перехода в активное предприятие; переход записывается в аудит. |
| Администратор предприятия | Все камеры, правила/зоны, анализ, LIVE, события, экспорт, статистика, сотрудники, роли и аудит своего предприятия. |
| Специалист по охране труда | Правила и зоны всех камер предприятия, анализ видео, подключение LIVE, разбор событий, экспорт и статистика. Не управляет сотрудниками. |
| Мастер / начальник смены | Эфиры, события, клипы и результаты проверки только назначенных камер участка. Нельзя назначить без камер. Не изменяет правила и роли. |
| Оператор / диспетчер | Просмотр эфиров и доказательств, журнал и очередь тревог, статусы «подтверждено / ложное / передано мастеру». Все или назначенные камеры. Не меняет настройки и сотрудников. |
| Работник / водитель | Памятка по безопасности и свой аккаунт. Без доступа к чужим видеозаписям, событиям или статистике. Подключение внешних световых/звуковых устройств остаётся отдельной интеграцией. |
| Служба охраны труда / юрист | Журнал, доказательства, экспорт, история действий; без изменения результатов проверки, камер или ролей. |
| Менеджмент | Агрегированная статистика; без кадров, клипов, сырых событий и управления. |

Права конкретизированы в `app/auth.py:ROLES`, одинаково возвращаются UI через `/api/roles`. Проверки серверные: скрытая кнопка не заменяет запрет endpoint. Скоуп камеры действует на чтение данных и файлов; специалист и локальный администратор имеют все камеры предприятия. Имена камер могут совпадать между предприятиями.

Кабинет платформы и окружение предприятия разделены в навигации. При переходе в активное предприятие открывается его рабочая страница, а глобальный раздел «Предприятия» скрывается. Кнопка «Кабинет администратора» в панели окружения сбрасывает серверный контекст предприятия и возвращает к управлению платформой. Сам рабочий контекст хранится в сессии и сохраняется при обновлении страницы.

Из кабинета платформы можно управлять сотрудниками любой выбранной карточки через `/api/platform/organizations/{org_id}/members` и соответствующие методы POST/PATCH/reset password. Только администратор платформы получает эти права; проверка принадлежности сотрудника предприятию и запрет изменения глобальных аккаунтов сохраняются. Скоуп такой операции действует только внутри запроса и не переключает окружение в сессии. Локальный администратор по-прежнему работает через `/api/members` только со своим предприятием. Счётчики различают активных, отключённых и общее число сотрудников; глобальные администраторы в штат предприятия не включаются.

## Подключение предприятия

1. На экране входа выберите «Заявка предприятия», укажите предприятие, контактное описание и собственные реквизиты локального администратора.
2. Пока заявка рассматривается, доступен только аккаунт и статус заявки.
3. Администратор платформы принимает или отклоняет заявку с причиной. Одобрение повторно рассмотренной заявки отклоняется сервером.
4. После одобрения локальный администратор добавляет сотрудников и передаёт им временные пароли лично. При первом входе сотрудник обязан сменить пароль.
5. При отклонении можно повторно подать заявку. Приостановленное предприятие возобновляет администратор платформы; его текущие обработки и эфиры останавливаются при приостановке.

Сотрудник привязан к одному предприятию. Полноценное членство одного человека в нескольких предприятиях, SSO и восстановление через email в эту реализацию не входят. Для приглашений администраторов есть SMTP-транспорт, сейчас замороженный в режиме локальной имитации: `docs/admin-invitations.ru.md`.

## Первое включение и существующие данные

Из папки проекта: `python scripts/create_admin.py`. Скрипт создаёт первого администратора платформы с собственным логином и скрытым вводом пароля. При наличии активного администратора повторный bootstrap запрещён. Веб-метода создания глобального администратора нет. Для общего localhost-демо пользователь отдельно разрешил публикацию фиксированных демонстрационных реквизитов: `DEMO-ACCESS.md`, `start-demo.cmd`. Они создаются только явным запуском, не при обычном старте сервера.

Миграция не удаляет прежние записи: им присваивается предприятие `legacy` («Локальный проект»). Выберите его в разделе «Предприятия». Перед обновлением сохраните локальную резервную копию `data/events.sqlite3` через SQLite backup; БД и медиа исключены из Git.

## Границы исполнения

- HTTP middleware устанавливает доверенный scope из серверной сессии, а не из тела запроса. Пользователь не выбирает organization_id для видео или события.
- Хранилище фильтрует jobs, events, cameras по предприятию и при необходимости камерам. У событий предприятие наследуется через job_id. Прямые ссылки `/media/runs/...`, отчёты, LIVE-view, остановка/отмена и экспорт проверяются отдельно.
- Только внутренние фоновые потоки и офлайн-инструменты работают без HTTP scope; принадлежность задания создаётся до запуска потока. Не используйте неограниченный доступ хранилища в новых HTTP handlers.
- Пароли: scrypt с индивидуальной солью, N=32768/r=8/p=3. Сессии: случайные токены, в БД SHA256 токена, cookie HttpOnly/SameSite=Strict, 12 часов. Пароль не хранится в браузере или localStorage.
- Изменения требуют CSRF-токен; cross-origin запросы отклоняются. Ограничены частота входа и регистрации. Изменение роли, отключение сотрудника и сброс пароля отзывают его сессии; текущий MJPEG-поток перепроверяет авторизацию.
- Удаление из команды мягкое: можно восстановить доступ, история остаётся. Последнего активного локального администратора нельзя отключить или понизить; проверка сериализована транзакцией.
- Результат проверки события хранит reviewed_by/reviewed_by_id, действие и время — в журнале аудита. Персональные секреты туда не попадают.

Сервер по умолчанию слушает только 127.0.0.1. Для доступа по сети нужны HTTPS и `SAFETY_SECURE_COOKIE=1`; прокси должен передавать корректный origin, не добавляйте универсальный CORS. Текущая SQLite-версия и глобальные лимиты вычислений рассчитаны на локальный прототип, а не на сотни одновременных предприятий. Нужны отдельные нагрузочные испытания и внешний security review перед промышленной публикацией.

## Проверки

`python -m pytest -q` включает проверки изоляции двух предприятий, прямых ссылок на чужие файлы и LIVE, экспорта ZIP/CSV, ролей, камер мастера, CSRF, временных паролей, отзыва сессий и последнего администратора. `node --test tests/test_camera_preview.cjs` проверяет освобождение устройства. Эти тесты не подтверждают качество нейросетевых сценариев или перенос на LinQ.
