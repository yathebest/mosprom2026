# Перенос на LinQ TPU

Реальное подключение отложено по просьбе пользователя, чтобы сохранить возможность работать с чатом. Локальный режим работает без VPN. OpenVPN Connect 3.9.0 установлен, профиль `LinQ-Hackathon` импортирован. Профиль исходного архива использует TCP 83.220.57.3:1194 и маршрут 10.0.114.0/24, игнорирует redirect-gateway. Секреты в проект не включены.

Первое соединение получило адрес туннеля, затем наблюдался NETWORK_EOF_ERROR. В тот момент маршрут к VPN-серверу проходил через AdGuard VPN. Причина не доказана; одновременное влияние VPN и DNS нужно проверять отдельно. На момент прекращения работ OpenVPN был отключён. Не отключать текущий рабочий интернет до готовности переключиться на стенд.

По документам это сервис **инференса LinQ TPU**, а не подтверждённо предоставляемая CUDA-машина для обучения. На локальном ПК уже есть RTX 4060 для обучения и экспериментов.

## Последовательность

### Что остаётся прежним после обучения

VPN, учётная запись Jupyter, штатный пример доступа и порядок аппаратных замеров не меняются. PDF-инструкция от 23.10 написана до получения Framework и успешной компиляции YOLO12m: её утверждения о неизученном SDK и отсутствии скомпилированной модели устарели. Подготовку модели выполняйте по этому документу.

До завершения Kaggle можно проверять стоковый COCO YOLO12m: готовая программа `data/linq/yolo12m/yolo12m-head-b1-o1-h1m.tpu`, соответствующий `yolo12m-tail.onnx`, `scales.json`, `thresholds.json` и отчёт `docs/yolo12m-compatibility.json`. На TPU выполняется head; tail, decode и NMS выполняются на хосте. Этот комплект ещё не проверен на оборудовании и не является обученным детектором касок/жилетов.

После полного обучения notebook экспортирует `person-yolo12m.onnx`, `ppe-head.onnx`, `ppe-vest.onnx`, два ONNX-классификатора и train-калибровку. Каждый новый детектор отдельно проходит разрез графа, калибровку, SDK-компиляцию и сравнение с ONNX. Классификаторы требуют собственной проверки и компиляции архитектуры ResNet; скрипт разреза YOLO к ним не применяется. Не смешивайте `.tpu`, tail, scales, порядок классов и preprocessing от разных checkpoint. Только после этого новый комплект заменяет старый на стенде. Для локального сайта проверенные веса устанавливаются в `data/models` по `docs/kaggle-training.ru.md`; это отдельный от запуска TPU режим.

## Контракт адаптера

`app/inference.py` задаёт один узкий интерфейс:

```python
class Backend:
    name: str
    def predict(self, bgr_frame: np.ndarray) -> list[Person]: ...
```

`Person` содержит bbox `(x1, y1, x2, y2)` **в пикселях исходного кадра**, confidence и необязательные COCO keypoints `17×3` `(x, y, confidence)`. track_id на этой границе не нужен. Общий ByteTrack назначает его после инференса.

Создайте собственный модуль, например `my_linq.py`, с `create_backend(confidence=...)`. Фабрика возвращает объект с `name` и `predict`. Запуск:

```powershell
$env:LINQ_ADAPTER='my_linq:create_backend'
python -m uvicorn app.server:app --host 127.0.0.1 --port 8765
```

Имя модуля задаётся локально, не через загруженные данные и не через UI. При ошибке адаптера прогон помечается failed, автоматической подмены на локальный инференс нет.

В `predict` выполняются:

1. Letterbox исходного BGR до размера модели с сохранением пропорций.
2. BGR→RGB, нормализация и порядок осей в соответствии с экспортом и SDK. Уточнить signed/unsigned, layout и scale квантованных тензоров.
3. Вызов документированного API LinQ для загруженной TPU-программы.
4. Деквантование, decode, NMS на хосте, обратное преобразование bbox/keypoints из letterbox в координаты исходника.
5. Возврат объектов Person, включая низкоуверенные боксы до порога .1 для второго прохода ByteTrack.

Локальный runtime API теперь известен из SDK: `pytpu.Device.list_devices()`, `Device.open(...)`, `device.load(program_path)`, `program.inference()` и `inference.sync(input_dict)`. Сам пакет `pytpu`, драйвер устройства и API удалённого сервиса в предоставленных 13 wheel-пакетах не обнаружены. Поэтому локальные вызовы нельзя автоматически выдавать за клиент удалённого хакатонного сервиса.

### Страницы и поддержанные архитектуры

Печатные страницы **35-36** соответствуют физическим страницам **39-40** PDF. Важные для продукта модели:

| Архитектура в списке SDK | Планируемая роль | Существенная оговорка |
|---|---|---|
| `yolo12m` | Основной усиленный детектор людей и отдельный детектор СИЗ | Есть специальный рецепт; часть графа переносится в postprocessing |
| `yolov8m_seg` | Независимый кандидат для детекции людей и масок | Это именно segmentation-модель; наличие в списке не доказывает поддержку всех YOLOv8 размеров и задач |
| `yolov8n_pose` | Поза и поведенческие признаки | Есть перечень узлов разреза; полный произвольный pose-экспорт не гарантирован |
| `resnet50`, `resnet152`, `efficientnet_b0` ... `efficientnet_b4` | Классификаторы видимых областей головы и торса после дообучения | Изменённая классификационная голова, размер входа и preprocessing требуют отдельной проверки |
| `yolo5s`, `yolo2/3/4`, SSD-варианты | Резервные архитектуры | У YOLO5s/SSD также есть сноски о разрезе графа |
| `yolo11n_obb` | Детекция повёрнутых объектов | Это OBB, не обычный YOLO11 detector и не pose |

Термин «поддержана» относится к конкретным графам и рецептам SDK. Дообучение, смена экспортера, размера входа, числа классов и версии архитектуры могут изменить совместимость. Для YOLO12 есть upstream v1 и turbo, поэтому фиксировать нужно commit, веса и экспорт, а не только строку `yolo12m`.

В SDK-тестах `onnx_direct_tests/test_unstable_networks.py` есть конкретные проблемные экспорты YOLO26 pose/seg, RF-DETR и RT-DETR с `GatherElements dynamic indices`, а также полный `yolov8n_pose.onnx` в перечне runtime errors. Это согласуется с необходимостью разреза pose-графа и не доказывает невозможность переноса любого варианта этих семейств. Наличие тестового рецепта `yolo26n_depth` также не означает поддержку YOLO26 detection/pose.

### Разрез графов

Сноска 4 для `yolo12m` задаёт выходы нейросетевой части:

```text
/model.21/Div_1_output_0
/model.21/Sub_1_output_0
/model.21/Sigmoid_output_0
```

Сноска 6 для `yolov8n_pose`:

```text
/model.22/Mul_6_output_0
/model.22/Concat_6_output_0
/model.22/Concat_5_output_0
/model.22/Sigmoid_1_output_0
/model.22/Concat_7_output_0
/model.22/Sigmoid_output_0

```

Это имена тензоров конкретного эталонного экспорта. Перед разрезом проверить их наличие и топологию, сопоставить полный ONNX с `head -> tail`, затем квантовать `head`. Метод `get_sub_model(model, ordered_input_names, ordered_output_names)` показан в разделе Sub model на печатных страницах 39-41. Decode, оставшиеся операции головы, NMS, обратное преобразование координат, трекинг, привязка СИЗ и правила могут исполняться на хосте. Фиксировать объём передаваемых промежуточных тензоров: он влияет на задержку удалённого сервиса.

### Квантование, компиляция и runtime

1. Статический ONNX с фиксированными входами; `compile.py` явно отвергает нулевые/dynamic размеры. Для начала `batch=1`, один размер входа. Другой размер или batch - отдельный артефакт и проверка.
2. `preliminary_model_conditioning`, затем `RegularModel(model=onnx_model)`. Сохранять `anchors_mapping`, поскольку имена ONNX и промежуточного представления могут отличаться.
3. `calibrate_torch(calibration_data=...)` собирает thresholds. Только репрезентативные train-данные с точным preprocessing. В `compile.py` случайные тензоры обозначены как демонстрационная заглушка. В примерах используются 2-4 изображения: этого недостаточно для независимой оценки и промышленной калибровки.
4. Рецепт `dnn_quant_tests/zoo_networks_tests/_quant_cases/yolo12m.py`: `case_batch=1`, `FLOAT16` для ReduceMax/ReduceMean/ReduceSum, `swish_mode=PIECEWISE_LUT`. Параметры необходимо воспроизвести через API установленной версии; обычный полностью INT8 режим не считать эквивалентом этого рецепта.
5. Сравнить max-based calibration с percentile-режимами на validation. SDK поддерживает `activation_percentile` и `samplewise_percentile`; увеличение числа калибровочных изображений при max-based оценке может ухудшить квантование из-за выбросов.
6. При необходимости `fine_tune_torch`: обучаются пороги активаций через distillation к FP32-выходам, веса остаются FP32. Это **не** замена полноценного обучения детектора на размеченных данных. Выбор параметров по validation, test не использовать.
7. `quantize(thresholds) -> save(.qm.onnx) -> as_torch_graph(...).export_to_pt2(...) -> Network.from_quantized_model(...) -> compiler.compile_(TPU_H1M, network, O1) -> TpuProgram.from_executable(...) -> to_file(.tpu)`.
8. Сначала O1, затем сравнить O5. Документация предупреждает, что O5 иногда создаёт некорректные программы или слишком долго компилируется; тогда вернуться к O1. В PDF также описаны O3 и O5_FGS; публичный `tpu_framework.__all__` экспортирует O1/O3/O5.
9. Сопоставить FP32 ONNX, квантованный reference, PT2 при его использовании, `.tpu` на устройстве и итоговые события. В SDK есть тест на расхождение PT2/FX с NaN: одного успешного экспорта недостаточно.
10. По умолчанию использовать runtime с metadata и автоматической упаковкой. Raw mode требует `convert_to_raw`, ручных `codec.encode/decode`; лишнее повторное масштабирование или упаковка недопустимы. CWL, batch, порядок осей и dtype брать из tensor descriptions.

`pytpu`-пример обращается к локальному `/dev/tpu*`. Для удалённого сервиса нужны его отдельный клиент, формат запроса и учёт времени передачи. TLM в документации назван внутренним отладочным инструментом, хотя связанные пакеты в архиве присутствуют. TLM FPS - оценка симулятора, не замер платы.

### Несогласованности и комплектность

- README предлагает `python compile_onnx.py`, но в архиве файл называется `compile.py`.
- Пакеты основного SDK имеют ABI `cp312` и платформу `linux_x86_64`; нативная Windows/Python 3.13 среда приложения им не подходит. У `hw_conv` wheel помечен `py3-none-any`, но внутри Linux `.so`, поэтому нельзя считать весь комплект платформонезависимым.
- Входящий `torch_resnet50.onnx` прошёл `onnx.checker`: opset 12, вход `input.1` FP32 NCHW `[1,3,224,224]`, выход `495` `[1,1000]`. Это классификатор ImageNet для проверки тракта, не детектор людей или касок.
- Quick start использует TensorFlow-style ResNet с NHWC, другим mean и именами `Placeholder:0`/`logits:0`. Для входящего **torch**-ResNet нужен NCHW и ImageNet mean/std, как в end-to-end примере. Эти варианты нельзя смешивать.
- Внутренние `/auto/...` пути, `dnnhub`, CI-ресурсы и демонстрационные изображения из PDF не поставлены как самостоятельный model zoo. Все перечисленные модели и веса в архиве отсутствуют, кроме torch-ResNet50.
- Вложенные RST и notebook содержат старые API-примеры; для этого релиза приоритет у текущих экспортов API, `compile.py` и PDF. Не копировать старый конструктор `QuantizedModel(original_graph_def=...)` без проверки.
- В metadata нескольких пакетов лицензия `UNKNOWN`; права на публичное распространение SDK из этого не следуют. Хранить в репозитории собственные адаптеры, инструкции, версии и хеши; бинарный SDK оставить локально.

## Если pose-граф не компилируется

Приоритет — совместимый детектор людей и полный конвейер зон/движения на LinQ. SDK-пример resnet50 нужен для проверки доступа, но запуск одной resnet50 вместо модели продукта не подтверждает перенос решения. Другую модель, её preprocessing и метрики явно указывать в отчёте.

Можно обрезать граф до поддерживаемой нейросетевой части, оставив decode/NMS на CPU. Вариант «CPU-поза + TPU-детектор» допустимо исследовать, но распределение вычислений нужно открыто показать экспертам. Точность маленьких моделей и маленьких входов на дальних людях проверять отдельно.

## Честный протокол сравнения

Один тестовый набор, одинаковые кадры, одинаковый размер входа и confidence/NMS. Отдельно: загрузка/прогрев, перенос тензоров по сети, собственно TPU-инференс, preprocessing, postprocessing, трекинг, правила и end-to-end. Сохранять версию SDK, хеши ONNX/TPU-программы, число потоков и ошибки. Не называть задержку RPC временем аппаратного ядра и не выдавать FPS RTX 4060 за показатели LinQ.


## Добавленная RGB-модель падений

`fall-resnet18.onnx`: статический FP32 NCHW вход1×3×224×224, выход1×2 логита (не лежит/лежит), opset12. BGR→RGB, PIL bilinear resize224×224, /255, ImageNet mean=[.485,.456,.406], std=[.229,.224,.225]. Softmax по двум логитам на хосте; probability[1] передаётся в `scene_state={'lying_probability':p,'scope':'scene'}`. Временные правила выполняются общим конвейером.

Адаптер backend может иметь `scene_state` после каждого predict. Если его нет, включённое правило падений использует экспериментальную геометрию позы, к которой метрики обученного RGB-классификатора не относятся. Не заявлять качество0,90 для такого варианта.

Нумерическая проверка ONNX и 6 входных тензоров только из train находятся в `docs/body_onnx_smoke.json` и `data/linq-calibration/`. Этих шести кадров недостаточно для репрезентативной INT8-калибровки. Используйте разнообразные train-кадры, исключите test. Команды компилятора и вызовы API нужно взять из SDK; ни один .onnx не является готовой TPU-программой.


## Дополнительные модели сценариев

Шесть исходных ONNX-графов: PPE13, fire/smoke, smoking, construction/machinery, COCO nano для ручной клади и COCO small для телефона. Формы, классы, хеши и источники — data/models/scenario-manifest.json. Локально используется ONNX Runtime CPU либо изолированный CUDA 12 профиль (см. README), без TPU-компиляции этих шести моделей. Нужные графы выбираются по RunConfig; телефон и СИЗ используют дополнительные crop-проходы, что нужно отдельно учитывать в бенчмарке.

Backend должен реализовать configure_scenarios(config) и после каждого predict выставлять objects_state: list[Observation], где Observation содержит исходные пиксельные bbox, confidence, нормализованный label и model. Дополнительные правила остаются на хосте. При отсутствии configure_scenarios включённая дополнительная модель вызывает явную ошибку вместо тихого пропуска сценария.
