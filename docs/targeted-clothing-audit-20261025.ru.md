# Аудит кандидата сигнальной одежды, 25.10.2026

**Решение: не устанавливать `signal-clothing.onnx` в автоматическое определение состояния.** Веса сохраняются кандидатом. Отдельный режим подсказки оператору можно проектировать позднее; сейчас его нет, положительный результат непосредственно участвует в подтверждении `worn` и снятии нарушения.

Проверены `candidate.json`, история 200 эпох, лог успешного экспорта, `train_signal_clothing.py`, метаданные ONNX, предобработка и интеграционный код. GPU и Kaggle не использовались; приложение, веса production и тренер не изменены.

## Почему два порога равны 1.01

Это предусмотренное защитное отключение классов, а не ошибка экспорта. Калибратор использует только validation: выбирает argmax с оценкой от 0.8 до 0.995, требует минимум 10 принятых примеров и эмпирическую precision не ниже 0.98 для `ordinary`, 0.95 для остальных. Если подходящего порога нет, записывает 1.01. `ordinary` и `unobservable` не прошли это условие; фактически используется лишь `hi_vis` с порогом 0.805. Пороги не менялись после просмотра test.

Обучение действительно завершило 200 эпох за примерно 48 минут. 250 минут — верхняя граница, а не требуемая длительность. Лучшая эпоха 184 выбрана по **сырому** validation macro F1 = 0.78284. До порогов validation precision/recall: `ordinary` 0.789/0.625, `unobservable` 0.696/0.667. Следовательно нулевые значения после порогов означают отказ выдавать эти классы, а не отсутствие обучения этих классов.

Train содержит 1137/118/93 примера hi_vis/ordinary/unobservable, validation — 197/24/24. Балансировка семплера повторяет малые классы, но не создаёт новые независимые примеры. Малый объём и разнообразие неоднозначных наблюдений, перенос с прежнего бинарного классификатора и различие доменов — возможные причины; причинный эксперимент не проводился. Значение softmax и выбор порога на используемой validation не являются гарантией вероятности безопасности или нижней статистической границей precision.

## Практическая CPU-проверка

ONNX Runtime, исключительно CPUExecutionProvider, 2 потока, PIL BILINEAR 224×224, ImageNet-нормализация. Использованы 245 validation и 232 отложенных test crop. Значения ниже — относительно подготовленной разметки; это не независимая экспертная сертификация и не метрики видеособытий.

| Проверка | Результат |
|---|---|
| Test, сырой argmax | macro F1 0.77932 |
| Test, неизменные пороги | hi_vis: TP194, FP5, FN3; precision 0.97487, recall 0.98477 |
| Ошибочно признанная сигнальная одежда | 2 из 22 ordinary; 3 из 13 unobservable |
| Factory validation | 16 из 18 hi_vis приняты; 0 из 9 прочих приняты |
| Factory test | отсутствует в этом подготовленном наборе |

Все 232 test crop проходят минимальную геометрию текущего адаптера: фильтр размера не устраняет эти 5 FP. В листе ошибок видны узкие, частично видимые, перевёрнутые и малодетальные наблюдения; оценки некоторых неверных результатов превышают 0.94. В автоматической логике такой позитив способен ошибочно снять нарушение после временного подтверждения. Поэтому высокая суммарная precision на преобладающем классе не оправдывает установку кандидата.

Для прежнего torso ResNet50 оценены **только принятые vest positives**; старое `no_vest` не считалось отсутствием светоотражающей рабочей формы. На общей подвыборке 227 людей с допустимым аннотированным PPE proposal: старый классификатор TP185/FP0/FN7, новый TP189/FP5/FN3. Геометрия моделей различается согласно обучению: старый — аннотированный vest proposal с контекстом1.3, новый — весь человек с контекстом1.05. Это сравнение классификаторов с готовой геометрией, не полноценного детектора или трекера. Ноль FP на этой подвыборке не гарантирует их отсутствия вне неё.

## Совместимость и ограничения

Метаданные кандидата соответствуют новой политике: яркий жилет **или визуально различимая светоотражающая рабочая форма** считаются подходящей одеждой. Текущая установка такого файла заменяет прежний torso-классификатор. При широкой политике отрицательные legacy `no_vest/no_safety_vest` заранее отбрасываются; они не перебьют новый положительный результат. Однако именно это делает ложный `hi_vis` достаточным голосом в пользу снятия признака нарушения. Сохраняем прежние положительные признаки и отказ от неподтверждённых отрицательных legacy-выводов.

Локальная ONNX validation воспроизвела **точно сырую матрицу ошибок** эпохи184, но при фиксированном пороге дала TP185/FP5 вместо отчётных TP186/FP6. Экспорт проверял FP32-parity лишь на нулевом тензоре. Проверка PyTorch на реальных crop начата, затем остановлена по просьбе родительского агента из-за нехватки ОЗУ и paging; результатов parity она не дала. Причина расхождения **не установлена**; переносить GPU/экспортные числа в локальный runtime без этой оговорки нельзя. Никаких порогов для устранения расхождения не подбирали.

Разбиение выполнено по source groups; после нормализации разделителей конфликтов между split не найдено. Factory validation составлена из original TRAIN видео; original factory TEST в обучение не переносился. Поведенческие префиксы factory-файлов не обозначают камеры. Сцены ранее рассматривались, камеры и актёры могут повторяться; это development validation, не camera-disjoint blind factory benchmark. Подготовленные upstream holdout не всегда совпадают с original native split; это раскрыто в исходном manual-review JSON. Test не использовали для обучения, калибровки или изменения разметки после получения ошибок.

## Артефакты и воспроизведение

Полный результат с индивидуальными вероятностями, SHA256, сырыми/пороговыми матрицами, разрезами доменов, итоговым `deployment_decision: reject` и ограничениями: `docs/targeted-clothing-comparison-20261025.json`.

Листы для ручного просмотра:

- `data/cache/targeted-completed-20261025/clothing-review/test-five-false-compliant.jpg`
- `data/cache/targeted-completed-20261025/clothing-review/factory-validation-27.jpg`

Повторяемый CPU-прогон с сохранением новых вычислений в отдельный файл:

```powershell
python scripts/compare_targeted_clothing.py --output data/cache/targeted-clothing-rerun.json
```

Поддерживаются `--data`, `--candidate-dir`, `--legacy-model`. Для восстановления точных legacy crop нужны исходный `ppe-expanded/manifest.jsonl`, исходные изображения и manual review; файлы моделей и подготовленного набора по умолчанию берутся из текущих локальных каталогов. Повторный прогон не меняет production и не калибрует test. При текущем дефиците памяти повторять его параллельно с NN-проверкой не следует.
